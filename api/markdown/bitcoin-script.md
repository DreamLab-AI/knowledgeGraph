- ### Definition
  - [[Bitcoin Script]] is the programmable spending-condition language that governs every output in the Bitcoin UTXO model. It is a Forth-like, stack-oriented language composed of [[Opcodes]] that push data and execute operations such as `OP_DUP`, `OP_HASH160`, `OP_CHECKSIG`, and `OP_CHECKMULTISIG`. The deliberate omission of loops makes Script provably terminating and resistant to denial-of-service through computational exhaustion. Spending a previous output requires supplying a scriptSig (or witness) that, when executed together with the locking scriptPubKey, leaves a non-zero value on the stack.

- ### Relationships
  - [[Bitcoin Script]] is a specialised [[Scripting Language]] that relies on [[Opcodes]] for execution and [[Digital Signature]] verification for authentication. It enables [[Lightning Network]] payment channels via hash-locked and time-locked outputs, and the Taproot upgrade extended Script with Schnorr-based operations that underpin [[Bitcoin Ordinals]] inscriptions. [[Hash Time-Locked Contract]] functionality is fundamental to cross-chain atomic swaps.

- ### Content
  - Satoshi Nakamoto designed Script as part of Bitcoin's original architecture released in January 2009. The decision to forgo Turing completeness was explicit: an unbounded scripting language would make fee estimation and denial-of-service prevention intractable. Several opcode groups — including `OP_CAT` and arithmetic operations beyond 32 bits — were disabled in 2010 following discovery of overflow vulnerabilities, and the set has remained stable since, with careful additions via Bitcoin Improvement Proposals.

  - The execution model involves two phases: the locking script (scriptPubKey) attached to an output describes the conditions for spending, and the unlocking script (scriptSig, or witness in SegWit) is supplied by the spender. Nodes concatenate and execute both; if the stack ends with a truthy value, the transaction is valid. Standard output types — P2PKH, P2SH, P2WPKH, P2WSH, and P2TR — are template patterns used by wallets, each with well-defined security and efficiency properties.

  - The ecosystem around Bitcoin Script includes libraries such as `bitcoinjs-lib`, `rust-bitcoin`, and `python-bitcoinlib`, plus hardware wallet firmware that constructs and verifies script conditions. P2SH introduced by BIP 16 allowed complex multisig and other conditions to be hidden behind a hash until spend time, reducing UTXO bloat. Taproot's MAST (Merklised Abstract Syntax Tree) extended this concept, enabling large policy trees where only the executed branch is revealed.

  - As of 2024–2025, the debate over re-enabling disabled opcodes — particularly `OP_CAT` — intensified. Proposals argue that restoring `OP_CAT` would enable covenants (spending conditions that constrain future transactions), enabling programmable vaults and novel layer-2 constructions without a soft fork to introduce entirely new opcodes. The outcome of this debate will significantly shape Bitcoin's programmability roadmap through the late 2020s.
